# Ten classic bad cases: measured diagnostics and fault handling

This audit combines real retrieval probes, independently checked source passages, and controlled generation/transport faults. No paid live generation model was configured. A controlled draft and prescribed reviewer verdict test the application's handling of a failure; they do not measure a model's hallucination rate or its ability to recognize that failure.

The important finding is that a plausible bad-case description is not necessarily a reproduced failure. NVIDIA's cash-flow row was already retrieved, and expanding that query made its final ranking worse. A Cummins result initially scored as an evidence miss contains a valid alternative source that the frozen labels omit. Neither observation justifies silently changing the benchmark or the production retrieval policy.

Results and provenance are published in [classic_bad_cases_results.json](../data/evaluation/classic_bad_cases_results.json). Reproduce the source and controlled checks with [run_bad_case_audit.py](../scripts/run_bad_case_audit.py); the separate [retrieval probe](../scripts/probe_bad_case_retrieval.py) runs the embedding and reranking interventions. The older [30-case catalog](../data/evaluation/failure_cases.json) remains a set of behavior specifications, not 30 measured incidents.

The initial audit passed **11/11 deterministic controls**, including two positive controls for a reported value and a supported future statement. Separately, [provider boundary results](../data/evaluation/provider_fault_results.json) reproduce four defects and record their corrected failure behavior. These counts describe different checks, not fifteen independently observed model errors.

Initial audit commit `4e303c0691b115710c83f9e1ef3b0a959a436765` passed **373 regression tests**, including 15 tests added for response handling and generation deadlines. The subsequent [fault-handling follow-up](../data/evaluation/fault_handling_followup_results.json) reproduced **five boundary probes across two fault families**—invalid Unicode and ambiguous HTTP framing—and added **seven regression tests**. At that time the follow-up code passed **380 tests** in an isolated snapshot of the committed baseline plus the follow-up changes; all **11/11 controlled audit checks also passed when rerun**. The existing tokenizer cache was reused, and no generation endpoint was contacted.

Historical audit, retrieval, and provider-result artifacts retain their original measurements and implementation hashes. Their SHA maps describe those recorded runs, not the current implementation. The follow-up artifact records its own baseline and changed-code fingerprints. Artifact hashes and retrieval metrics were checked separately against their recorded source files and rankings.

## Source checks

All page numbers below are **one-based PDF pages**. Table row indices are zero-based. The result artifact retains source hashes and exact locators; quotations and numbers should be interpreted with their source headings. Parsed sources under `data/processed/` are generated locally by `scripts/parse_reports.py` and are not in Git.

- **NVIDIA cash payments:** FY2025 parsed tables (`data/processed/NVDA/NVDA_FY2025_annual_report/tables.jsonl`), p148 table1 row31: `Payments related to repurchases of common stock | (33,706) | (9,533) | (10,039)`. Caption: `(In millions)`, with years ended January 26, 2025 / January 28, 2024 / January 29, 2023. FY2025 cash paid is **$33,706 million**, an outflow. The p125:e10 narrative instead reports repurchasing 310 million shares for **$34.0 billion**; it does not replace this cash-flow amount.
- **Microsoft scope and fiscal columns:** FY2024 parsed tables (`data/processed/MSFT/MSFT_FY2024_annual_report/tables.jsonl`), p48 table1 row0 establishes 2024 / 2023 / 2022. Row4 gives revenue 245,122 / 211,915 / 198,270; row9 gives gross margin 171,008 / 146,052 / 135,620; row13 gives operating income 109,433 / 88,523 / 83,383, all in millions. The p35 summary repeats the FY2024 inputs. Analyst calculation `171008 / 245122 * 100 = 69.7644%` is an audit interpretation, not a reported percentage or (at audit time) an enabled generator calculation. Parsed prose (`data/processed/MSFT/MSFT_FY2024_annual_report/pages.jsonl`), p35:e13 explicitly says **Microsoft Cloud** gross margin decreased to **71%**. The summary's **17%** is gross-margin growth, another distinct quantity.
- **Forecast versus actual:** NVIDIA FY2025 tables (`data/processed/NVDA/NVDA_FY2025_annual_report/tables.jsonl`), p144 table1 rows1–2 identify FY2025 revenue **130,497 million** alongside prior years. These historical figures cannot support an invented FY2027 forecast. All 27 parsed elements containing `2027` in the five NVIDIA reports were inspected; matches concern compensation, leases, amortization, tax items, and future schedules. This targeted text check is not an exhaustive semantic or visual absence guarantee. FY2025 prose (`data/processed/NVDA/NVDA_FY2025_annual_report/pages.jsonl`), p137:e3 does explicitly expect increased FY2026 capital expenditure, so future statements remain eligible when supported.
- **Comparison and parse quality:** Intel FY2024 prose (`data/processed/INTC/INTC_FY2024_annual_report/pages.jsonl`), p32:e18 gives **32.7%**, with nearby FY2024 chart labels. AMD FY2024 tables (`data/processed/AMD/AMD_FY2024_annual_report/tables.jsonl`), p51 table1 row4 gives **49% / 46%**, with FY2024 / FY2023 headings. Intel's p65 table1 is explicitly `structured_reliable=false`; `candidate_rows` are debug data. Its source fallback retains revenue **53,101** and gross margin **17,345** as repeated intact tokens, consistent with the rounded percentage. The corruption was already contained before this audit.
- **Cummins alternate support:** FY2021 parsed tables (`data/processed/CMI/CMI_FY2021_annual_report/tables.jsonl`), canonical p32 table1 row0 and alternate p61 table1 source text both report **24,021 / 19,811 / 23,571 million** for FY2021 / FY2020 / FY2019. The latter is headed `CONSOLIDATED STATEMENTS OF NET INCOME`; its `NET SALES` source line and caption survive in the retrieved fallback. Treating that result as having no useful answer evidence confuses annotation coverage with source support.

## Measurement boundaries and remaining work

The four exploratory retrieval probes use the existing 56,525 chunks from 200 reports, normalized BGE-M3 embeddings, Flat retrieval, and the pinned BGE reranker. Each final pool contains at most 20 passages. Reranking always receives the unchanged original question and unchanged source text. Sixteen pools, **320 pairs**, were scored without truncation. These selected examples do not estimate general recall improvements; no production expansion setting or frozen benchmark label was changed.

Expanded-vector retrieval recovered the particular p48 Microsoft rows and p32 Cummins row in the final Top 5, raising their exact-location metrics. Their original Top 5 already contained independently checked alternatives, so those increases are not evidence that previously unanswerable questions became answerable. Conversely, all three NVIDIA interventions displaced the exact cash-payment row from the final Top 5. Report both improvements and regressions before adopting expansion.

For Microsoft's operating-income query, the measured warm components were **47.3 ms** for query embedding, **67.6 ms** for Flat Top-100 search plus payload retrieval, and **286.1 ms** for Top-20 reranking. Their **401.1 ms sum is a component estimate**, measured in separate stage processes, excluding generation, semantic verification, source binding, queueing, and startup. Cold setup was recorded separately: encoder load/warmup 45.15 s, index verification/load 5.93 s, reranker load/warmup 18.38 s. Reusing resident models avoids including those setup operations in every warm request, but no production speedup is claimed here.

A separate source-binding probe used one Microsoft FY2024 p48 statement chunk. Building a fresh source store took **329.3 ms**; the median of five subsequent calls using that same store was **7.6 ms**. This measures reconstruction and integrity checking for one chunk only. It is neither a full Top-5 request nor model latency and should not be added to the earlier component estimate as though the stages were one measured request.

The `generate_answer(..., deadline_seconds=3)` example starts its budget **after retrieval**. Monotonic checks surround source binding, generation, reference validation, semantic verification, verdict validation, and rendering. An active synchronous call cannot be forcibly interrupted; its late result is discarded after it returns, and later stages do not start. Provider socket timeouts are separate. This is a cooperative generation safeguard, not a hard three-second end-to-end limit.

The controlled regression advances an injected monotonic clock by four seconds inside generation. Against baseline commit `ba6fc6e99e55ff69c96542e6f44c84ac55f10322`, the old API returned an answer and invoked semantic review once. The patched API with the optional three-second budget returns `deadline_exceeded`, no citations, and no semantic-review call. Its recorded elapsed time is still four seconds; this demonstrates safe late-result handling, not cancellation or a one-second performance gain.

The existing confidence diagnostic also explains why refusal needs separate measurement. At frozen raw-logit threshold **6.359375**, 15/50 test questions were accepted, of which 11 had complete annotated evidence; seven other questions with complete annotated evidence were refused. Thus neither a high score nor a low score establishes correctness or answerability. The threshold remains provisional and is not changed by these probes. See [generation gate results](../data/evaluation/generation_gate_results.json).

The later [live bad-case audit](live_bad_cases.md) ran a configured `gpt-4.1-mini` generator and verifier on 50 designed questions (7 expecting a refusal) with agent grading; independent human review and measurement on held-out questions remain open. In particular, this audit's semantic failure fixtures prescribe the review verdict; they establish application control flow rather than the reliability of a real reviewer model.

## Reproduce and use the deadline

From the repository root, with the existing local source corpus and retrieval artifacts available:

```powershell
.\.venv\Scripts\python.exe scripts/run_bad_case_audit.py --publish data/evaluation/classic_bad_cases_results.json
```

The audit consumes the published source audit, retrieval comparison, and provider-boundary results. It reruns the eleven controlled checks and the source-binding timing probe without contacting a generation endpoint. For a fresh GPU retrieval comparison, run the separate stages with the already cached models:

```powershell
.\.venv\Scripts\python.exe scripts/probe_bad_case_retrieval.py --stage all
```

Once an endpoint, model, credentials, and an explicit confidence policy are configured as described in [generation setup](generation_constraints.md), an application can opt into the generation budget through `generate_answer(..., deadline_seconds=3)` or the existing answer CLI:

```powershell
.\.venv\Scripts\python.exe scripts/answer_question.py --question-id dev-001 --gate-policy data/experiments/generation_gate/policy.json --deadline-seconds 3 --output data/experiments/generation/dev-001.json
```

The CLI example uses the provisional diagnostic gate by explicit choice; it does not install that gate as a production default. The output includes stage timings and the generation-budget audit. A refusal still returns the structured result and exits with code 2.
